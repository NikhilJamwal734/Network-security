# API-009.8 — Cross-Platform Advanced Configuration Review

## Scope and compatibility

Implemented for the four registered platform IDs: `cisco_asa`, `fortios`, `snort`, `suricata`.

- New, opt-in `POST /api/v1/analyze/assessment` returns the existing **normalized report** with one extra `assessment` object.
- Existing `/api/v1/analyze`, `/api/v1/analyze/universal`, and `/api/v1/analyze/normalized` endpoints and their response formats **remain unchanged**.
- The endpoint reuses the existing upload validators, platform selection logic, parser adapters and normalizers. Uploaded content is parsed as inert text and **never executed**.
- React dashboard displays the common assessment panel for all four platforms. Existing platform-specific pages and normalized PDF report remain available; PDF gains an assessment section when the PDF renderer is installed.
- No extra dependencies are required for the backend. For normalized PDF export, continue using the existing `jspdf` dependency.

## Platform assessment coverage

| Platform | Config evidence observations | Preexisting security checks reused | Critical unavailable coverage |
| --- | --- | --- | --- |
| Cisco ASA | Access-rule, network-object, service-object, NAT, route counts | Existing Cisco ASA analyzer | Effective/runtime traffic, IDS signatures |
| FortiOS | Visible policies, address-object, service-object, interface counts | Broad accept, disabled logging, plaintext management, visible interface/policy concerns | VDOMs, expanded groups, effective policy order/defaults |
| Snort | Inline-rule count, HOME_NET visibility, include count, output-directive count | Duplicate SID, broad pass, missing SID, rule syntax | Included rule-file contents, effective loaded rules, Snort 3 Lua, runtime IDS |
| Suricata | Inline-rule count, HOME_NET visibility, YAML rule-file references, AF-PACKET entries, EVE output setting | Duplicate gid/sid, broad pass rules, malformed *active* rule detection | Referenced rule-file contents, complete YAML semantics, runtime IDS/IPS |

**Visibility observations are not new security findings**; they are derived from parsed allowlisted fields and do not silently add Medium/High findings. Where there is no reliable value, the status is `not_assessed` rather than a guessed zero. Only referenced file *counts* are shown; referenced paths are not opened.

## Provisional configuration-review score

`assessment.review_score.value` is a limited triage indicator, **not** `summary.security_score`, not an independently validated security grade, and not a cross-vendor comparison metric.

- Start at 100 points. Deductions per finding: Critical −15, High −7, Medium −3, Low −1, Info −0, Unknown −0.
- Clamp to the range 0–100.
- If the normalized coverage identifies *any* `not_assessed` domain, the upper bound is **80**.
- Always emit `status: provisional`, `comparable_across_platforms: false`, a full breakdown, and the relevant not-assessed domains.
- A result such as **80/100 with zero findings** means "no weighted findings within the implemented checks, with major unknowns". It does **not** establish that the device is secure.

The original platform score in `summary.security_score` is retained, unchanged (Cisco ASA has its legacy score; other vendors may return `null`). The two metrics must not be merged or presented as interchangeable.

## Installation — PowerShell

Run these commands from **the main project root**:

```powershell
cd "C:\IoT\Information security\project 2\config analyzer"

Expand-Archive `
  -LiteralPath "$env:USERPROFILE\Downloads\API-009.8-Four-Platform-Assessment.zip" `
  -DestinationPath "." `
  -Force

.\.venv-win\Scripts\python.exe .\scripts\install_api_009_8.py

.\.venv-win\Scripts\python.exe -m pytest -q tests/test_api_009_8_assessment.py
.\.venv-win\Scripts\python.exe -m pytest -q
```

The installer adds `assessment_router` to `app/api/main.py` and backs up the existing file as `app/api/main.py.api0097.backup`. It refuses unknown main.py layouts.

Enable the shared dashboard assessment panel:

```powershell
.\.venv-win\Scripts\python.exe .\frontend_patch\scripts\install_frontend_assessment.py
cd .\frontend
npm run build
npm run dev
```

The frontend installer runs against `frontend/src/` (not the project root `src/`). Existing files are backed up with `.api0098.backup` suffix and only changed once. If it detects an unknown page layout, it stops instead of blindly replacing the dashboard. It modifies `frontend/src/api/universal.ts`, `frontend/src/pages/UniversalAnalysis.tsx`, and (if present) `frontend/src/utils/normalizedPdf.ts`; it adds `AdvancedAssessmentPanel.tsx` and CSS.

## Accuracy and limitations

- A PDF with zero findings does not warrant a "safe" badge, even when the provisional review score is 80.
- Suricata 8 YAML is not completely parsed by this subset, Snort 3 Lua is outside scope, FortiOS VDOM/effective access is outside scope, and Cisco ASA is limited to its existing static checks.
- No referenced rule-file paths are traversed, no vendor commands executed, no traffic replayed.
- This milestone adds a consistent cross-platform review and scoring layer; it does **not** implement exhaustive new vendor grammar, full rule-file bundling, or live device verification.
