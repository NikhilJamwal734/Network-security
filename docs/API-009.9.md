# API-009.9 — Explicit IDS Rule Bundles & PDF Code Splitting

## Design

This is an opt-in extension to the verified API-009.8 platform analysis. It does
not modify the schema of any previous endpoint and does not assign a score to
additional rule-file evidence.

### IDS rule file workflow

`POST /api/v1/analyze/ids-bundle?platform=suricata|snort` accepts multipart:

- `rules`: 1–8 explicitly uploaded `.rules` files. Each is validated for UTF-8,
  control characters, line-length/count limits and a maximum of 2 MiB using the
  existing Snort rule upload reader.
- `config`: optional uploaded `.conf`/`.cfg`/`.txt` or Suricata `.yaml`/`.yml`
  text. Its content is validated using the established reader and selected
  platform checks.
- Maximum combined validated text is 4 MiB.
- Names must be simple filenames without directories. Duplicate filenames are
  rejected case-insensitively.

The files are parsed independently and checked together for duplicated enabled
IDs: SID for Snort, `(gid,sid)` for Suricata. Individual findings include the
name and line number of the uploaded file. Existing supported rule checks are
reused. Disabling/commenting a rule does not create a duplicate-enabled SID.

### Rule file reference visibility

The main Snort config may contain `include /some/path/file.rules`, and the
Suricata YAML may contain a top-level `rule-files` list. The new route compares
only **inert reference basenames** with uploaded filenames. The reference text
is never followed on disk, and the API labels any basename equality as an
unverified candidate match. If any rule-file entries were not supplied, the
report explicitly describes them as not uploaded.

It cannot verify effective rule loading, runtime detection, inline prevention,
full Snort 3 or Suricata grammar, or that a source with the same name is the
source used in production.

### PDF lazy loading

The installer removes the static `import { jsPDF } from "jspdf"` in
`frontend/src/utils/normalizedPdf.ts` and dynamically imports `jspdf` inside
`downloadNormalizedPdf`. This lets Vite place PDF logic behind a user action,
instead of forcing it into the initial synchronous dependency chain.

The React dashboard also adds `IDSRuleBundlePanel` within the normalized result
section for Snort/Suricata. The panel is an explicit second step. Rule bundle
findings are not silently merged into the original normalized findings, score,
legacy Cisco exports, or PDF report. That can be considered as a separate
future report-provenance milestone.

## Verification

- 30 new pytest cases in `tests/test_api_009_9_ids_bundle.py`
- Existing API-009.8 / Suricata false-positive cases checked in an isolated
  compatibility workspace (84 passed in the combined selection).
- The frontend installer was run twice against a staged unified dashboard;
  the second invocation made no changes.
- The new component passed strict TypeScript checking using a component harness.
- A smoke test with the user's previously uploaded Suricata YAML returned 0
  `SURICATA-008` false positives and reported one filename candidate match out
  of two visible referenced rule-file entries.

The full existing 784 tests and actual Vite production build remain to be
verified in the user's current local project.
