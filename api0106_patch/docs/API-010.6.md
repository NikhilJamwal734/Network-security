# API-010.6 — Object Reference Integrity and Evidence

## Purpose

Additional, opt-in, upload-scoped object reference diagnostics layered on the
existing API-010.5 result. The endpoint is `POST /api/v1/analyze/object-assurance`
and returns all upstream report fields, plus an `object_assurance` field. The
existing object-resolution, correlation, severity and assessment endpoints
remain unchanged.

## What is actually checked

**Cisco ASA**

- Repeated `object network NAME` declarations within the supplied text, with
  paired declaration source lines. A repeated block may be an intentional edit;
  the tool does **not** assume it is invalid.
- Missing *uploaded-source* network-object declarations referenced by recognized
  `access-list ... extended permit|deny` ACE address selectors.
- The analyzer intentionally does not classify service-object references as
  missing network objects, does not infer object-group support, and does not
  check all possible ASA command variants.

**FortiOS**

- Repeated `edit NAME` entries in recognized `firewall address`, `addrgrp`,
  `service custom`, `service group` and `policy` tables.
- Source/destination address and addrgrp member references not defined in the
  analyzed upload. Built-ins `all` and `all6` are not flagged as missing.
- Unresolved policy service names are classified separately as
  `service_definition_not_visible` because they might be built-ins.
- Cyclic `firewall addrgrp` membership within the recognized config subset,
  using a bounded recursive traversal with one observation per cycle.
- VDOM configurations and unsupported mutation/nested contexts are not
  evaluated as a complete effective policy.

**Snort & Suricata**

- Explicitly `not_assessed` for object dependency resolution. The older IDS
  correlation and other checks continue independently.

## Interpretation and confidence

Diagnostics describe what is visible in the **uploaded text only**. `not_defined_in_upload`
means the declaration was not found in that upload, not that it is absent from
an active appliance, missing from every included file, or unsafe in production.
When text is truncated or processing was limited, the status becomes `limited`
and missing references are labeled `not_visible_in_excerpt`.

`object_assurance.summary` contains:

- `definitions_seen`, `references_checked`, `observations`, `missing_in_upload`
- `cycles`, `repeated_definitions`, `incomplete`, `observations_omitted`

Each observation contains `reference` (OA-001...), `kind`, `object_name`,
`line_number`, `related_line_numbers`, `explanation`, and `recommendation`.
The output is supplemental only and never modifies previous risk findings,
score calculations, correlation candidates or the uploaded configuration.

## Boundaries

The endpoint captures up to 2 MiB before calling API-010.5, because the earlier
analyzer may close the upload. The core scanner processes a maximum of 50,000
lines, 5,000 checked references and 100 serialized observations. Beyond these
caps it reports incompleteness rather than treating omitted input as evidence
of absence. No live device communication, filesystem follow-up or arbitrary
configuration execution occurs.

## Testing

From the root of the Windows project after installing:

```powershell
.\.venv-win\Scripts\python.exe -m pytest -q tests\test_api_010_6_object_assurance.py
.\.venv-win\Scripts\python.exe -m pytest -q
cd frontend
npm run build
```

The package compatibility workspace passed 53 API-010.5+API-010.6 tests and an
isolated TypeScript check. Those checks do **not** substitute for the user
running the full tests and Vite build on their exact project tree.
