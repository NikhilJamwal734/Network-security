# API-010.8 — Conservative NAT, Routing and Reachability Evidence

## Purpose

This additive API stage extends the installed API-010.7 chain. It **never overwrites** earlier report fields or recalculates normalized findings/severity/score. It appends a `nat_route_reachability` object to the existing result.

`POST /api/v1/analyze/nat-route-reachability` accepts multipart `file`, optional `platform`; it snapshots up to 2 MiB of source bytes **before** handing the upload to the API-010.7 analysis chain (which may close the file). The frontend changes **only** the API endpoint, adds a compact dashboard snippet, and inserts a comprehensive PDF-only evidence section.

## Scope of verified syntax

| Input | Supported subset | Excluded / must validate on device |
|---|---|---|
| Cisco ASA | `route interface IPv4 netmask gateway [distance]`; `ipv6 route interface CIDR gateway [distance]`; simple `object network` `host`/`subnet`; `nat (real,mapped) static <IP>` on single-host objects; explicit inbound `access-group`; narrow `access-list … extended permit/deny ip|tcp|udp` with `any`, `host`, `object`, IPv4 masked pair and numeric destination port | NAT sections, object NAT precedence, PAT, twice NAT, ranges, source ports, aliases, ACL flags, access-list execution order, zones, route tracking, ECMP, PBR, interfaces being up |
| FortiOS | Single-domain `config router static` IPv4 with explicit gateway and device, default destination if missing; simple `config firewall vip` IPv4 host-to-host mapping; single-interface `config firewall policy` using explicit VIP, simple defined `config firewall address`, or `all` as destination; `set nat enable` as SNAT indicator | VDOMs, central SNAT, dynamic route state, VIP port-forward, pool expansion, service/rule execution semantics, groups, negation, zones, local-in rules, PBR, SD-WAN, policy movement, IPv6 routing for this stage |
| Snort / Suricata | Prior normalized report retained; this new review marked `not_assessed` | Forwarding/NAT/routing not assessed for IDS/IPS configuration files |

**Interpretation**: The engine reports *configured candidates*, not actual effective reachability. The route lookup is longest-prefix *within the supported static routes in the uploaded text only*, requiring a unique best result covering the entire selected destination network. A more-specific route overlapping part of a destination causes abstention. Dynamic routes, link status, NAT rule order, SD-WAN and vendor packet-processing are unmodeled. No route candidate is not proof of isolation.

## API report shape

`nat_route_reachability`:

- `status`: `reviewed_subset` / `limited` / `not_assessed`.
- `summary`: total and successfully parsed routes/NATs; policies found/eligible; evidence items; omitted items; completeness flag.
- `evidence[]`: bounded records (`NRR-001`, etc.) with `kind`, source line, optional policy and route line, destination/translated addresses, ingress/egress labels, explanatory technical text, confidence and remediation guidance.
- `limitations[]`: scope and uncertainty statements.

Route candidate labels include `route_policy_candidate` and `potential_egress_discrepancy` (conditional—**not** proof of broken routing). NAT evidence includes `configured_static_nat_candidate`. All confidence is deliberately `configured_candidate_only`.

## Dashboard / report split

**Dashboard only**: counts for parsed routes, NAT mappings, eligible policies and evidence snippets; at most two short `NRR-*` kind labels. Nothing resembling complete evidence, line-by-line analysis, advisory rationale or recommendations should be rendered in the dashboard.

**Formal PDF**: every returned evidence item with precise line references, route and policy IDs, destination/mapped address, interface selectors, explanation, recommendations, and all limitations and coverage disclaimers. Previous PDF chapters remain unchanged. Output bounded to 100 evidence items per upload; overflow explicitly makes the report limited.

## Guardrails

- Uploaded text only; no device access, no command execution, no external includes, no packet simulation.
- UTF-8 input snapshot capped at 2 MiB. At most 40,000 lines, 400 source records, 100 eligible policies, and 100 report evidence items.
- Structural parsing anomalies, duplicate definitions, ambiguous selectors, route ties and split-route coverage are excluded. Missing context leads to abstention, not fabricated active state.
- The frontend installer fails *before making edits* if known API-010.7 code anchors cannot be matched. The backend installer follows the same fail-before-write rule.
- Neither installer modifies the sidebar/theme, previous compact review panels, score calculation, nor Snort/Suricata analysis code.
