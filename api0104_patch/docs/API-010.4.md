# API-010.4 — Evidence Integrity & Ordering Review

## Purpose

API-010.4 adds an opt-in static verification layer **after** API-010.3 rule correlation. It does **not** change existing normalized findings, provisional scores, severity counts, or API-010.3 correlation candidates. It is a report-quality aid, **not** a vendor-complete security analysis or a traffic simulator.

### New endpoint

`POST /api/v1/analyze/correlation-assurance` — multipart upload fields: `file` (required) and `platform` (optional). Its response preserves the previous API-010.3 report and adds a `correlation_assurance` object.

**Upload safety:** A bounded 2 MiB sample is captured and the upload rewound **before** the existing API-010.3 analyzer receives the file, because canonical analysis closes the uploaded file. Existing validation errors and scoring logic are retained. No uploaded configuration text is executed, no referenced file is opened, and no automatic configuration edit is made.

### What it verifies

- **All platforms:** The reported pair lines exist within the sampled source and have the expected basic vendor-rule structure. "Source references located" does **not** mean the underlying configuration or security finding has been independently validated.
- **Cisco ASA:** If both named ACL entries have explicit `access-list NAME line N extended ...` labels, compare their sequence numbers. A pair listed earlier in the source with a *higher* line label is flagged `ordering_contradicted`. The old `shadowed_candidate` still exists in the unmodified API-010.3 output; API-010.4 warns that its inferred ordering is unsupported.
- **Fortinet FortiOS:** Explicit policy `edit` references are checked, but VDOM context, object expansion, device policy order and actual traffic are unresolved.
- **Snort / Suricata:** Both cited rule starts are checked without assuming equal rule headers imply equal signatures or actions. Full options and deployed engine behavior remain outside scope.

### Status vocabulary

| Status | Interpretation |
|---|---|
| `ordering_contradicted` | Explicit ASA ACL labels disagree with the source ordering assumed by the correlation |
| `order_supported_candidate` | Explicit labels agree; still not proof of active binding or effective policy |
| `order_unverified` | No sufficiently comparable explicit ASA sequence |
| `object_resolution_required` | FortiOS references exist, but policy meaning cannot be established solely from labels |
| `ids_options_unverified` | IDS header matches do not establish full rule equivalence |
| `evidence_unavailable` | At least one cited line could not be located/recognized in the bounded source sample |

### Limits

The audit inherits API-010.3's rule subset and truncation limitations; audits at most 70 pairs, 50,000 source lines and a 2 MiB upload sample. It does not model NAT, route tables, ASA ACL binding, VDOMs, object/group expansion, TCP state, IDS content matching or runtime enforcement. The frontend and PDF show **advisory verification**, never "confirmed conflict."

### Endpoint test

Visit `http://127.0.0.1:8000/docs` after restarting the backend and select `POST /api/v1/analyze/correlation-assurance`. Upload a known configuration. Confirm `correlation_assurance.summary` exists and `rule_correlation` and `findings` remain present.

### Rollback

The backend installer saves `.before_api0104.bak` for modified files. Restore `app/api/main.py` from its backup, delete `app/api/correlation_assurance.py` and `app/core/correlation_assurance.py`, and restart FastAPI. The frontend installer likewise saves `.before_api0104.bak` for changed files. Restore those backups and remove `src/components/CorrelationAssurancePanel.tsx` and `.css`; rebuild the frontend. Do not delete the API-010.3 upload fix.
